## 📝 ЕТАП 2: ENTITY КЛАСИ

### Архітектура Entity для ВСІХ варіантів

**Загальні правила:**
1. Кожен варіант має **3 основні Entity** в Stage 1:
   - **Category** — категорія (зброї/матеріалів/техніки/підрозділів)
   - **Item** — конкретна одиниця (зброя/матеріал/транспорт/персонал)
   - **Location/Person** — місце/особа (склад/водій/підрозділ)

2. Всі Entity **мають однакові базові поля:**
   - `id` (Long) — primary key
   - `createdAt` (LocalDateTime) — дата створення
   - `updatedAt` (LocalDateTime) — дата оновлення

3. Всі Entity **використовують Lombok:**
   - `@Data` — для getters/setters/toString
   - `@NoArgsConstructor` — конструктор без параметрів
   - `@AllArgsConstructor` — конструктор з усіма параметрами

4. Всі Entity **мають Auditing:**
   - `@EntityListeners(AuditingEntityListener.class)` на класі
   - `@CreatedDate` на `createdAt`
   - `@LastModifiedDate` на `updatedAt`

---

### Приклад структури Entity (загальний шаблон)

**⚠️ ЦЕ НЕ ГОТОВИЙ КОД! ЦЕ ШАБЛОН ДЛЯ РОЗУМІННЯ!**

```java
package ua.edu.viti.military.entity;

import jakarta.persistence.*;
import lombok.AllArgsConstructor;
import lombok.Data;
import lombok.NoArgsConstructor;
import org.springframework.data.annotation.CreatedDate;
import org.springframework.data.annotation.LastModifiedDate;
import org.springframework.data.jpa.domain.support.AuditingEntityListener;

import java.time.LocalDateTime;

@Entity
@Table(name = "ВАШ_ВАРІАНТ_categories")  // <- ЗМІНІТЬ
@EntityListeners(AuditingEntityListener.class)
@Data
@NoArgsConstructor
@AllArgsConstructor
public class ВашCategory {  // <- ЗМІНІТЬ назву класу

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true, length = 100)
    private String name;

    @Column(length = 500)
    private String description;

    // === ДОДАЙТЕ СПЕЦИФІЧНІ ПОЛЯ ДЛЯ ВАШОГО ВАРІАНТУ ===

    @CreatedDate
    @Column(nullable = false, updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;
}
```

### Приклад JPQL запиту з JOIN FETCH

**Проблема N+1:** Якщо ви робите:
```java
List<SupplyItem> items = repository.findAll();
for (SupplyItem item : items) {
    System.out.println(item.getCategory().getName()); // <- N окремих запитів!
}
```

**Рішення — JOIN FETCH:**
```java
@Query("SELECT i FROM ВашItem i JOIN FETCH i.category WHERE i.status = :status")
List<ВашItem> findByStatusWithCategory(@Param("status") ItemStatus status);
```

Це **один** запит замість N+1!

## 💼 ЕТАП 4: DTO КЛАСИ

### Навіщо потрібні DTO?

**Проблема використання Entity напряму:**
```java
// ❌ ПОГАНО - повертаємо Entity з контролера
@GetMapping("/{id}")
public ResponseEntity<SupplyItem> getItem(@PathVariable Long id) {
    return ResponseEntity.ok(itemService.findById(id));
}
```

**Чому це погано:**
1. **Циклічні залежності** — Entity має зв'язки, Jackson не може серіалізувати
2. **LazyInitializationException** — коли спробуєте звернутися до lazy поля
3. **Надмірна інформація** — не всі поля треба показувати клієнту
4. **Змішування concerns** — Entity для БД, DTO для API

**Рішення — DTO:**
```java
// ✅ ДОБРЕ - повертаємо DTO
@GetMapping("/{id}")
public ResponseEntity<ItemResponseDTO> getItem(@PathVariable Long id) {
    return ResponseEntity.ok(itemService.findById(id));
}
```

---

### Типи DTO

**Для кожного Entity створюємо 3 типи DTO:**

1. **ResponseDTO** — для відповідей API (GET)
   - Містить **всі** поля що треба показати клієнту
   - Включає вкладені об'єкти (CategoryDTO всередині ItemDTO)
   
2. **CreateDTO** — для створення (POST)
   - **БЕЗ** `id` (буде згенерований)
   - **З** валідацією (@NotNull, @NotBlank, @Size...)
   
3. **UpdateDTO** — для оновлення (PUT)
   - **З** `id`
   - Тільки поля що **можна** змінювати

#### CategoryCreateDTO

package ua.edu.viti.military.dto.request;

import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;
import lombok.AllArgsConstructor;
import lombok.Data;
import lombok.NoArgsConstructor;

@Data
@NoArgsConstructor
@AllArgsConstructor
public class SupplyCategoryCreateDTO {

    @NotBlank(message = "Назва категорії обов'язкова")
    @Size(max = 100, message = "Назва не може бути довшою за 100 символів")
    private String name;

    @NotBlank(message = "Код категорії обов'язковий")
    @Size(max = 20, message = "Код не може бути довшим за 20 символів")
    private String code;

    @Size(max = 500, message = "Опис не може бути довшим за 500 символів")
    private String description;

**Важливі анотації валідації:**
- `@NotNull` — не може бути null
- `@NotBlank` — не може бути null, порожнім рядком або тільки пробілами
- `@Size(min=X, max=Y)` — обмеження довжини
- `@Min`, `@Max` — для чисел
- `@Email` — для email
- `@Pattern(regexp="...")` — регулярний вираз

## 🛠️ ЕТАП 5: SERVICE LAYER

### Архітектура Service Layer

**Service Layer відповідає за:**
1. **Бізнес-логіку** — перевірки, розрахунки, правила
2. **Маппінг** Entity ↔ DTO
3. **Управління транзакціями** (@Transactional)

- HTTP запити/відповіді (це Controller)

### CRUD методи в Service

#### 1. CREATE (створення)

**Алгоритм:**
```
1. Валідувати вхідні дані (автоматично через @Valid)
2. Перевірити унікальність (batchNumber/registrationNumber/militaryId)
3. Якщо вже існує → кинути DuplicateResourceException
4. Знайти пов'язані Entity (Category, Warehouse...)
5. Якщо не знайдено → кинути ResourceNotFoundException
6. Створити новий Entity об'єкт
7. Заповнити поля з DTO
8. Задати початковий статус
9. Зберегти в БД через Repository
10. Конвертувати Entity → ResponseDTO
11. Повернути DTO
```

**Приклад реалізації:**

```java
@Transactional  // Це операція зміни даних - знімаємо readOnly
public SupplyItemResponseDTO create(SupplyItemCreateDTO dto) {
    log.info("Creating new supply item with batch number: {}", dto.getBatchNumber());
    
    // 1. Перевірка унікальності
    if (itemRepository.existsByBatchNumber(dto.getBatchNumber())) {
        throw new DuplicateResourceException(
            "Матеріал з партією " + dto.getBatchNumber() + " вже існує"
        );
    }
    
    // 2. Знайти категорію
    SupplyCategory category = categoryRepository.findById(dto.getCategoryId())
        .orElseThrow(() -> new ResourceNotFoundException(
            "Категорію з ID " + dto.getCategoryId() + " не знайдено"
        ));
    
    // 3. Знайти склад (якщо вказано)
    Warehouse warehouse = null;
    if (dto.getWarehouseId() != null) {
        warehouse = warehouseRepository.findById(dto.getWarehouseId())
            .orElseThrow(() -> new ResourceNotFoundException(
                "Склад з ID " + dto.getWarehouseId() + " не знайдено"
            ));
    }
    
    // 4. Створити Entity
    SupplyItem item = new SupplyItem();
    item.setName(dto.getName());
    item.setBatchNumber(dto.getBatchNumber());
    item.setCategory(category);
    item.setQuantity(dto.getQuantity());
    item.setUnit(dto.getUnit());
    item.setExpirationDate(dto.getExpirationDate());
    item.setHazardClass(dto.getHazardClass());
    item.setStorageConditions(dto.getStorageConditions());
    item.setWarehouse(warehouse);
    item.setStatus(ItemStatus.IN_STOCK);  // Початковий статус
    
    // 5. Зберегти
    SupplyItem saved = itemRepository.save(item);
    log.info("Supply item created with ID: {}", saved.getId());
    
    // 6. Конвертувати в DTO
    return toResponseDTO(saved);
}
```

**Важливі моменти:**
- `@Transactional` без `readOnly` — це операція зміни
- Логування важливих подій через `log.info()`
- Викидання виключень при помилках
- Коментарі для читабельності

### GlobalExceptionHandler

```java
package ua.edu.viti.military.exception;

import lombok.extern.slf4j.Slf4j;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.context.request.WebRequest;

import java.time.LocalDateTime;
import java.util.HashMap;
import java.util.Map;

@RestControllerAdvice  // Глобальний обробник для всіх контролерів
@Slf4j
public class GlobalExceptionHandler {

    /**
     * Обробка ResourceNotFoundException (404)
     */
    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleResourceNotFound(
            ResourceNotFoundException ex,
            WebRequest request) {

        log.error("Resource not found: {}", ex.getMessage());

        ErrorResponse error = new ErrorResponse();
        error.setType("/errors/resource-not-found");
        error.setTitle("Resource Not Found");
        error.setStatus(HttpStatus.NOT_FOUND.value());
        error.setDetail(ex.getMessage());
        error.setInstance(request.getDescription(false).replace("uri=", ""));
        error.setTimestamp(LocalDateTime.now());

        return ResponseEntity
                .status(HttpStatus.NOT_FOUND)
                .body(error);
    }

    /**
     * Обробка DuplicateResourceException (409 Conflict)
     */
    @ExceptionHandler(DuplicateResourceException.class)
    public ResponseEntity<ErrorResponse> handleDuplicateResource(
            DuplicateResourceException ex,
            WebRequest request) {

        log.error("Duplicate resource: {}", ex.getMessage());

        ErrorResponse error = new ErrorResponse();
        error.setType("/errors/duplicate-resource");
        error.setTitle("Duplicate Resource");
        error.setStatus(HttpStatus.CONFLICT.value());
        error.setDetail(ex.getMessage());
        error.setInstance(request.getDescription(false).replace("uri=", ""));
        error.setTimestamp(LocalDateTime.now());

        return ResponseEntity
                .status(HttpStatus.CONFLICT)
                .body(error);
    }

    /**
     * Обробка BusinessLogicException (400 Bad Request)
     */
    @ExceptionHandler(BusinessLogicException.class)
    public ResponseEntity<ErrorResponse> handleBusinessLogic(
            BusinessLogicException ex,
            WebRequest request) {

        log.error("Business logic error: {}", ex.getMessage());

        ErrorResponse error = new ErrorResponse();
        error.setType("/errors/business-logic");
        error.setTitle("Business Logic Violation");
        error.setStatus(HttpStatus.BAD_REQUEST.value());
        error.setDetail(ex.getMessage());
        error.setInstance(request.getDescription(false).replace("uri=", ""));
        error.setTimestamp(LocalDateTime.now());

        return ResponseEntity
                .status(HttpStatus.BAD_REQUEST)
                .body(error);
    }

    /**
     * Обробка валідаційних помилок (400 Bad Request)
     */
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidationErrors(
            MethodArgumentNotValidException ex,
            WebRequest request) {

        Map<String, String> validationErrors = new HashMap<>();

        ex.getBindingResult().getFieldErrors().forEach(error -> {
            validationErrors.put(error.getField(), error.getDefaultMessage());
        });

        log.error("Validation errors: {}", validationErrors);

        ErrorResponse error = new ErrorResponse();
        error.setType("/errors/validation");
        error.setTitle("Validation Failed");
        error.setStatus(HttpStatus.BAD_REQUEST.value());
        error.setDetail("Помилки валідації вхідних даних");
        error.setInstance(request.getDescription(false).replace("uri=", ""));
        error.setTimestamp(LocalDateTime.now());
        error.setErrors(validationErrors);

        return ResponseEntity
                .status(HttpStatus.BAD_REQUEST)
                .body(error);
    }

    /**
     * Обробка всіх інших помилок (500 Internal Server Error)
     */
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleGenericError(
            Exception ex,
            WebRequest request) {

        log.error("Unexpected error occurred", ex);

        ErrorResponse error = new ErrorResponse();
        error.setType("/errors/internal");
        error.setTitle("Internal Server Error");
        error.setStatus(HttpStatus.INTERNAL_SERVER_ERROR.value());
        error.setDetail("Внутрішня помилка сервера");
        error.setInstance(request.getDescription(false).replace("uri=", ""));
        error.setTimestamp(LocalDateTime.now());

        return ResponseEntity
                .status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body(error);
    }
}
```

**Як це працює:**
1. Виникає виключення в Service
2. Spring перехоплює його
3. Шукає відповідний `@ExceptionHandler`
4. Створює `ErrorResponse`
5. Повертає клієнту з правильним HTTP статусом

- ID в шляху: `/items/{id}` не `/items?id=1`

## ✅ ЕТАП 8: BEAN VALIDATION GROUPS

### Навіщо потрібні Validation Groups?

**Проблема:** Різні вимоги при створенні та оновленні:

```java
// При створенні - всі поля обов'язкові
{
  "name": "Патрони",       // ✅ обов'язково
  "batchNumber": "BATCH1", // ✅ обов'язково
  "quantity": 5000         // ✅ обов'язково
}

// При оновленні - всі поля опційні (partial update)
{
  "quantity": 4500  // ✅ OK, оновимо тільки кількість
}
```

**Рішення — Validation Groups:**

**При створенні - валідуємо групу OnCreate:**

```java

- `@Valid` - валідує всі constraints без групи
- `@Validated(OnCreate.class)` - валідує тільки constraints з цією групою
- `@Validated(OnUpdate.class)` - валідує тільки constraints з цією групою

**Приклад: валідатор для перевірки майбутньої дати**

package ua.edu.viti.military.validation;

import jakarta.validation.Constraint;
import jakarta.validation.Payload;

import java.lang.annotation.*;

@Target({ElementType.FIELD})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = FutureDateValidator.class)
@Documented
public @interface FutureDate {
    String message() default "Дата має бути в майбутньому";

    Class<?>[] groups() default {};

    Class<? extends Payload>[] payload() default {};
}
```

**Імплементація:**

```java
package ua.edu.viti.military.validation;

import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;

import java.time.LocalDate;

public class FutureDateValidator
        implements ConstraintValidator<FutureDate, LocalDate> {

    @Override
    public boolean isValid(LocalDate value, ConstraintValidatorContext context) {
        if (value == null) {
            return true; // null перевіряється через @NotNull
        }
        return value.isAfter(LocalDate.now());
    }
}
```

## 🆘 TROUBLESHOOTING

### Помилка: "Could not autowire. No beans found"

**Причина:** Repository/Service не сканується Spring

**Рішення:**
1. Перевірте що пакет знаходиться в `ua.edu.viti.military` або підпакетах
2. Перевірте анотацію `@Repository` / `@Service`
3. Перевірте що main клас має `@SpringBootApplication`

---

### Помилка: LazyInitializationException

**Причина:** Спроба доступу до lazy поля поза транзакцією

**Рішення:**
1. Додайте `@Transactional(readOnly = true)` на Service клас
2. Або використайте JOIN FETCH в Repository

---

### Помилка: ConstraintViolationException

**Причина:** Порушення constraint БД (унікальність, NOT NULL)

**Рішення:**
1. Перевірте чи не намагаєтесь створити дублікат
2. Перевірте чи всі обов'язкові поля заповнені
3. Подивіться детальне повідомлення помилки

---

### Помилка: JSON parse error

**Причина:** Циклічна залежність при серіалізації

**Рішення:**
1. НЕ повертайте Entity з Controller
2. Використовуйте DTO
3. Видаліть `@JsonBackReference` / `@JsonManagedReference` (це legacy)

---

### Помилка: Validation не спрацьовує

**Причина:** Немає `@Valid` в контролері

**Рішення:**
```java
public ResponseEntity<ItemDTO> create(
    @Valid @RequestBody ItemCreateDTO dto) {  // <- @Valid обов'язково!
```

---

### Swagger UI не відкривається

**Причина:** Неправильний URL або порт зайнятий

**Рішення:**
1. Перевірте що додаток запущений
2. URL: `http://localhost:8080/swagger-ui.html` (не `/index.html`)
3. Перевірте логи на помилки

---

### БД не підключається

**Причина:** Docker контейнер не запущений або неправильні credentials

**Рішення:**
```bash
# Перевірити статус
docker-compose ps

# Перезапустити
docker-compose restart postgres

# Подивитися логи
docker-compose logs postgres

# Перевірити application.properties
```

## 🎓 ПОРАДИ ВИКЛАДАЧА

### Типові помилки курсантів

1. **Повертають Entity з Controller замість DTO**
    - Призводить до циклічних залежностей
    - Розв'язка: завжди використовуйте DTO

2. **Забувають `@Valid` в контролері**
    - Валідація не спрацьовує
    - Розв'язка: `@Valid @RequestBody`

3. **Використовують `@Enumerated(EnumType.ORDINAL)`**
    - При додаванні нових значень порушується порядок
    - Розв'язка: завжди `EnumType.STRING`

4. **Не додають `@Transactional` на методи Service**
    - LazyInitializationException
    - Розв'язка: `@Transactional` на класі та методах

5. **Забувають перевіряти існування перед оновленням**
    - NullPointerException
    - Розв'язка: `.orElseThrow()`

6. **Копіюють код замість розуміння**
    - Не можуть пояснити що робить код
    - Розв'язка: читайте документацію, експериментуйте
